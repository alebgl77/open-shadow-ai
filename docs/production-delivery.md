# Reproducible delivery and security gates

Third-party Python dependencies are committed in `requirements/*.txt` as exact versions with SHA256 hashes. Local ShadAI projects are built from this checkout; neither `shadai` nor `shadai-agent` is downloaded from PyPI. Official bases and externally pulled services use an exact version plus the SHA256 digest of their multiarchitecture index. Four services use maintained local recipes whose sources, compiler, modules and APK bytes are pinned separately; CI measures and gates their actual output images. These inputs freeze dependency selection and base content without promising identical wheel/container bytes, timestamps or OS build output across machines.

## Python locks

| File | Supported target / purpose |
|---|---|
| `runtime.txt` | Backend and agent runtime dependency closure, Python 3.12+, universal platform markers |
| `development.txt` | Runtime plus normal backend test/lint dependencies, Python 3.12+ |
| `agent.txt` | Standalone endpoint agent including optional Docker collection, Python 3.10+ |
| `build.txt` | Fixed pip 26.2.1, setuptools 84.0.0, wheel 0.48.0 and their closure |
| `tools.txt` | Maintenance only: uv 0.11.16 and pip-audit 2.10.1 plus their closure |

The first runtime/development resolution retained compatible versions already validated in the previous environment. Linux-only uvloop is resolved and hashed with its platform marker; it is absent on Windows. The standalone agent is resolved separately at its lower Python bound. The universal lock is not a claim that every Python implementation/future release has suitable binary wheels: CI actually exercises Linux amd64/arm64, Python 3.12/3.13 backend gates, Windows 3.13 native guards and Python 3.10 standalone installation.

Use a fresh environment, install the build toolchain and the chosen closure with pip hash checking, then build the local projects without resolving dependencies or fetching another build backend:

```sh
python -m venv tmp/delivery-env
# Use tmp/delivery-env/bin/python on Linux or Scripts/python.exe on Windows.
python -m pip install --only-binary=:all: --require-hashes -r requirements/build.txt
python -m pip install --only-binary=:all: --require-hashes -r requirements/development.txt
python -m pip install --no-deps --no-build-isolation . ./agent
python -m pip check
python scripts/lock-dependencies.py --check
```

Run these commands with the fresh environment's Python, not an unrelated activated environment. Third-party locks install wheels only, so an unavailable platform wheel fails instead of fetching unpinned third-party build dependencies. Runtime Docker builders follow the same sequence using `runtime.txt`, then copy only the runtime prefix into the final nonroot image. The test image installs `development.txt`. Application users, read-only roots, collector private spool ownership, Compose secret handling and network boundaries are unchanged.

`manifest.json` fingerprints the dependency lists, extras, Python lower bounds, build requirements, tool inputs and resolver parameters; it also fingerprints each lock's bytes. `--check` works offline and fails on metadata/lock drift. Normal lint settings and descriptions do not trigger needless dependency changes. Regeneration resolves all files in an isolated directory before replacing working locks; an interrupted copy cannot silently pass the manifest check.

For a reviewed update, install the hash-checked tools into a separate maintenance environment and run:

```sh
python -m pip install --only-binary=:all: --require-hashes -r requirements/tools.txt
python scripts/lock-dependencies.py --upgrade-package PACKAGE
python scripts/lock-dependencies.py --verify
python scripts/lock-dependencies.py --check
```

An ordinary regeneration preserves existing exact versions; `--upgrade-package` deliberately allows only the named package to move subject to metadata constraints. Edit the relevant project dependency first when its bound must change. Review every transitive change and platform marker. Updating uv itself requires updating `UV_VERSION`, `tools.in`, the complete tools lock and the manifest together with fresh regeneration evidence. The generator explicitly uses public PyPI, ignores inherited pip/uv index and override environment variables, disables automatic Python downloads and keeps its cache under ignored `tmp/production-delivery`. See [uv locking](https://docs.astral.sh/uv/pip/compile/) and [universal resolution](https://docs.astral.sh/uv/concepts/resolution/).

## Offline Windows agent

On the actual deployment Python/platform, install the hash-checked `build.txt` tools in a disposable authoring environment and run:

```sh
python scripts/build-agent-wheelhouse.py --output tmp/agent-wheelhouse
```

The output directory must be new. The script downloads only hash-allowed target wheels, builds the local agent with the fixed backend and no dependency/network resolution, records its SHA256 in `local-agent.txt` and `SHA256SUMS.json`, then proves a fresh installation using `--require-hashes --no-index --find-links`. Synthetic batching/import checks run with Python isolated from the source checkout. This is platform-specific: build separate wheelhouses for Windows/Linux and the deployment Python version/architecture; a Windows 3.10 wheelhouse is not a Windows 3.13 wheelhouse.

`Install-AgentWindows.ps1` retains its existing protected-directory/ancestor ACL checks, protected staged-wheel SHA256 verification, and `--no-index --find-links` installation. Provide its `WheelSha256` from the reviewed wheelhouse manifest and deploy only that new wheelhouse, with administrative ownership and no additional/unreviewed wheels. The installer verifies the local agent wheel but does not independently apply `agent.txt` to every dependency: the complete wheelhouse's reviewed hashes and protected content are part of its operator contract. Its native SYSTEM/task/DACL behavior remains covered by the existing Windows gates, rather than inferred from a package-resolution test.

`requirements/images.json` distinguishes official build-only bases/tools, the externally pulled Prometheus 3.15.0 runtime and four maintained runtimes. It records official Python 3.12.15 slim-trixie, Node 22.23.3 Alpine 3.24, nginx-unprivileged 1.30.5 Alpine 3.24, PostgreSQL 16.15 Alpine 3.24, ClickHouse 25.8.33.6 Alpine, Redis 7.4.11 Alpine 3.21 and node_exporter 1.12.1 bases. Python's previously mutable `3.12-slim` alias already resolved to trixie when pinned; the supported Node major and service release lines remain the same. Tool pins include official Go 1.26.6 Alpine 3.24, Trivy 0.75.0, BuildKit 0.33.1 and the Docker BuildKit Syft scanner 1.12.0. GitHub Actions are pinned to independently verified release commits; Buildx is fixed at 0.37.2.

The [maintained recipe notice](../requirements/service-builds/NOTICE.md) and `requirements/service-builds/manifest.json` bind the four Dockerfiles, release archive commits/SHA256, exact module graph and native Alpine APKs. PostgreSQL replaces gosu 1.19 with the same release source compiled using Go 1.26.6 and the locked x/sys 0.44.0 patch. node_exporter retains 1.12.1 source with x/crypto 0.56.0 and only its required module changes, and reports `1.12.1-shadai.1`. Redis replaces libcrypto3/libssl3 with 3.3.7-r2; ClickHouse uses 3.5.9-r0 because the minimum fixed 3.5.8-r0 libcrypto3 is unavailable on arm64. Each APK's bytes are SHA256-checked and its official signature is verified by `apk add --no-network` against the exact runtime base's trusted keys. Go modules use the official checksum database, a readonly graph and disabled automatic toolchain downloads.

The recipes additionally pin zlib 1.3.2-r1 for PostgreSQL/ClickHouse on Alpine 3.24 and Redis on Alpine 3.21, targeting the retained MEDIUM CVE-2026-85091 findings. All four official APK archives have independent SHA256/size pins and observed signature members; the runtime installation still performs native APK signature checks offline. PostgreSQL fetches the APK using the compiler stage's native `apk --print-arch`, then mounts it read-only for installation before the unchanged gosu privilege smoke. Its closed source graph verifies that exact additional mount and build-stage edge. The local change remains pending native builds on both architectures, exact installed-version/SBOM checks and complete final-runtime scans; it does not claim removal of lower-layer bytes or an already clean image. The unfixed GO-2026-5932 finding remains visible, and all existing query, severity, provenance and qualification gates remain mandatory.

Compose uses `pull_policy: build` and `shadai/SERVICE:VERSION-maintained.1` local tags bound to those recipes. These tags identify the maintenance recipe and are not immutable output digests or published signatures. No image is pushed or deployed by this CI. Kubernetes still requires externally supplied, verified immutable image references. Runtime users and entrypoints are inherited from the pinned official bases; Compose preserves private volumes and read-only deployment contracts. Replacing files does not remove their original bytes from lower layers.

```sh
python scripts/verify-image-pins.py
python scripts/verify-image-pins.py --registry
```

The registry check fetches only public official registry metadata, verifies both the exact tag and immutable digest against the raw index SHA256, and requires Linux amd64 plus arm64 for every official base/tool/runtime. Local recipe tags have no registry digest to check. The offline check rejects unknown roles/names, mutable bases, deployed build-only images, unbound recipes and changed source/module/APK input hashes. For an update, review the supported publisher patch, raw index/platforms, exact sources and module difference; refresh the recipe manifest and bump its recipe/tag together. Run the service contract tests, actual Compose and both native architecture builds. Updating a service image does not qualify existing database volumes: retain backups and test PostgreSQL/ClickHouse/Redis restore and migration on copied data before any production rollout. In particular, the earlier ClickHouse 25.x migration is not retroactively proven safe by pinning the current patch.

Mandatory CI builds each API/worker/collector/test/frontend image and each PostgreSQL/ClickHouse/Redis/node_exporter maintained runtime natively on amd64 and arm64 into 18 OCI archives, using the pinned BuildKit and SBOM generator. BuildKit adds SPDX SBOM and SLSA provenance attestations. `verify-oci-evidence.py --platform linux/amd64` (or `linux/arm64`) checks every blob SHA256 and every reachable index, manifest, config and layer descriptor for presence, size and media type. The image descriptor and config must match the explicitly selected native platform. Only a linked BuildKit attestation may use `unknown/unknown`; both the current OCI artifact layout with an empty config and the legacy image-config layout are supported. Both attestations must refer to the exact image manifest and statement subject digest. Missing image/config/layer bytes, unlinked statements, duplicate or unsafe archive paths and mismatched subjects fail. Layer hashing streams bytes; JSON documents are bounded to 128MiB (above BuildKit's 80MiB predicate limit), index depth to 16, graph descriptors to 10,000 and archive members to 100,000. OCI archives, evidence summaries and image advisory reports are retained as CI artifacts for seven days. These are build evidence and are not a claim of bit-for-bit binary reproduction. The attestation layout follows [BuildKit's pinned attestation storage contract](https://github.com/moby/buildkit/blob/v0.33.1/docs/attestations/attestation-storage.md) and [SBOM generator protocol](https://docs.docker.com/build/metadata/attestations/sbom/).

On internal pushes to `main`, a separate `signed-image-evidence` job waits for all mandatory jobs, downloads the exact scanned OCI archives, rechecks their evidence/hash, and creates official GitHub/Sigstore SLSA attestations with `actions/attest` 4.2.2 pinned to its release commit. Only this job receives `id-token: write` and `attestations: write`; no persistent signing key, registry image push or release is created. GitHub CLI 2.102.0 is downloaded from its official release and its archive SHA256 is checked against the reviewed publisher checksum before extracting only the regular verifier binary. Verification enforces the artifact digest, repository, signing workflow, source ref/commit and GitHub-hosted runner. The Sigstore bundle and verification result are retained separately. Signing or verification failure fails the internal push; a missing signature is not reported as success.

Pull requests, including external forks, always run OCI evidence, dependency, image and platform gates. They do not run the signing job because their token does not have trusted attestation permissions. Therefore PR artifacts are unsigned and signed evidence becomes available only after a successful internal `main` push. Public GitHub repositories support these [official ephemeral attestations](https://github.com/actions/attest); availability in a private repository depends on its GitHub plan and must be qualified separately.

After downloading a signed archive and its matching bundle, verify with the reviewed CLI, substituting the exact repository, source ref and commit that were accepted:

```sh
gh attestation verify runtime.oci.tar --repo OWNER/REPOSITORY \
  --signer-workflow OWNER/REPOSITORY/.github/workflows/ci.yml \
  --source-ref refs/heads/main --source-digest EXPECTED_COMMIT \
  --deny-self-hosted-runners --bundle sigstore-bundle.json --format json
```

The [official verification command](https://cli.github.com/manual/gh_attestation_verify) validates the signature and identity; a BuildKit JSON predicate alone cannot substitute for it. CI contract tests require commit-pinned actions, a single permission-scoped signing job, successful preceding gates, the exact OCI subject and these verification constraints. Fresh CI execution remains necessary to establish an actual signed attestation; local unit tests do not produce one.

## Mandatory advisory and monitoring gates

The pinned Grype 0.120.1 producer serializes its database schema with the literal `v` prefix: status uses `v6.x.y`, and import metadata records the client's exact `v6.1.10`. Validation preserves these original strings and their bound bytes; an unprefixed or incompatible schema is refused. The official [schema formatter](https://github.com/anchore/grype/blob/6f8d854af29d3a3086b11a84afa51554a2a245fe/internal/schemaver/schema_ver.go#L68) and [import producer](https://github.com/anchore/grype/blob/6f8d854af29d3a3086b11a84afa51554a2a245fe/grype/db/v6/import_metadata.go#L90) define this representation. Freshness, source URL, owned path, checksum, frozen database and advisory checks still apply independently.

The existing backend, offline sensor, frontend, real Windows guards and Compose integration steps remain mandatory. Additional jobs verify reproducible lock regeneration, public registry pins, offline standalone agent installation on all three runner platforms, image evidence and runtime vulnerability gates. Prometheus is checked in its actual container with `promtool check config --lint-fatal` and `check rules --lint-fatal`; deterministic alert fixtures run using the pinned image with no network and read-only mounted monitoring files.

The pinned pip-audit tool queries public package/version advisory metadata for every Python closure, without installing audited dependencies. Coverage must exactly match the names and versions from the hash-checked lock after evaluating every platform marker on the job's actual interpreter; a Windows-only dependency remains required on Windows. Empty reports, skipped packages, duplicates, missing packages and wrong versions fail. Runtime and standalone-agent findings fail for high/critical advisories with published fixes; an available fix with missing or unrecognized severity also fails closed pending review. Public GitHub advisory severity is fetched by advisory ID. The frontend stores both full tooling and runtime npm advisory reports and checks their dependency count against the package lock; the runtime report gates fixable high/critical findings.

Maintained binaries outside Trivy's versioned package inventory require separate, explicit queries through Grype 0.120.1. Its official amd64/arm64 release archive hashes and source commit are fixed in `requirements/component-scanner.json`; the publisher checksum and API agree, but this is not a claim that the release asset's signature was verified. PostgreSQL, Redis and BusyBox retain their original generic SPDX identities and every recorded CPE. The two exact gosu/node_exporter main-module observations retain `UNKNOWN`, their original PURLs, binary paths, sourceInfo, file checksums, layer identifiers and SPDX relationships. Their queried release versions come from the reviewed build source, while `binary_version_claim` remains null. Unrecognized or additional identityless/unversioned packages fail rather than receiving an invented version or ecosystem alias.

For those two source projections, `component_source.py` compares the embedded recipe bytes and three locked module files to the reviewed manifest, requires the complete typed BuildKit download/build/COPY/licence/smoke graph, and anchors its terminal ordered layer stack to the selected OCI manifest. JSON types must agree recursively: booleans, integers and floats cannot substitute for flags, ports, compatibility versions or descriptor sizes. The recorded graph hash covers the validated observed graph. Docker-gzip and OCI-gzip media types may differ only for the explicitly supported pair with identical digest and size. Disconnected steps, changed ports, destinations, commands, environment, mounts, inputs, recipe hashes or output stacks fail. BuildKit VCS fields remain unauthenticated observations of the invocation until the later GitHub archive/evidence signatures are verified; they do not authenticate the JSON predicate independently.

ClickHouse's principal binary is absent from the captured SPDX and Trivy inventories. The gate preserves that absence with `original_spdx_ids: []` and requires a separate declared ClickHouse 25.8.33.6 CPE query. It binds the exact five-node current recipe, official native-platform base and complete ordered output layers to the selected OCI subject. Every maintained service first exports only the OCI archive with its SBOM and maximum provenance. ClickHouse then performs a separate local Docker export through the same pinned action and builder with identical context, recipe, tag and native platform, with provenance and SBOM disabled and no registry push. This second step is bounded to five minutes and runs only after the first succeeds. Its tag, action image ID and metadata are not proof; only the original archive supplies the subject, SPDX, provenance and source graph.

`observe-clickhouse-version.py` requires the locally loaded image ID to equal the original selected OCI config digest, with matching OS, architecture, ordered uncompressed RootFS diff IDs and exact image environment before and after observation. This binds configuration and uncompressed contents across separate exports; it does not claim one attested invocation, identical compressed manifest bytes, a cache hit or cryptographic publisher authentication. A failed export or mismatch refuses the observation without another build, pull or equivalence fallback. A private UUID container runs only `/usr/bin/clickhouse server --version`, with no network, a read-only root, an unprivileged user, dropped capabilities, resource limits and one bounded tmpfs suppressing the declared image volume. Exact stdout, empty stderr, exit state, immutable container identity and verified removal are required before the separate receipt is written. Its observed CLI version is separate from an observed SBOM version; this association does not prove binary source reproduction or a publisher signature. Both collector and shared process-module hashes are bound and rechecked. The ten required component queries per architecture comprise PostgreSQL three, node_exporter four, Redis two and ClickHouse one, in addition to the two controls in each native service invocation. Actual native exports, CLI observations and scans on both architectures remain mandatory CI evidence.

The CLI receipt is Linux-only and commits under the exact canonical filename with one terminal `renameat2(RENAME_NOREPLACE)`. Until every process, container, layout, file and directory cleanup, source/hash check and deadline guard succeeds, its bytes exist only as a private UUID `.pending` file; the scanner and evidence verifier reject pending filenames even if their JSON says `verified`. All ancestors must be real root/current-user directories without group/world write or sticky permissions, with a current-user-owned output parent on an explicitly supported local filesystem (ext4, XFS, Btrfs, tmpfs or overlayfs). Unsupported kernels, NFS, CIFS, unknown filesystems and unsafe namespaces fail closed without an overwrite fallback or permission changes. After the successful exclusive rename, the collector performs no further I/O or cleanup. This relies on the trusted hosted CI user and root not replacing that namespace during the final pathname checks and rename; it does not resist a hostile same-user process, certify crash durability of the rename, or prove the collector's later exit status. CI still requires the actual collector step and every mandatory job to succeed. Precommit failures may retain only nonaccepted pending diagnostics; a concurrent canonical file is never overwritten.

Each native maintained-service gate runs real known-vulnerable CPE and Go controls before accepting the component queries. Direct literal query receipts bind every original SPDX assignment to its exact report hash, archive/manifest/config/platform, SBOM/provenance blobs and source proof. Grype matches are advisory findings, never a substitute package inventory. Trivy's native OS and versioned Go dependency inventory must still equal the independently generated expected inventory exactly. Both tools retain low/medium and unfixed findings, including GO-2026-5932 where reported; neither removes another tool's findings. A published fix with high, critical, missing, unknown or unrecognized severity fails the gate. Complete, valid coverage with failing advisories may retain metadata explicitly marked `verdict: failed`; signing refuses it.

The controls use the same validator during collection and evidence replay. After validating the exact query, tool, configuration, database, findings and ignored-match policy, a required CVE may match the original finding ID or a related advisory in that same finding whose namespace is exactly `nvd:cpe` and whose source is its canonical NVD detail URL. Present related metadata, including known CVSS, exploited-vulnerability, EPSS and CWE fields, is checked against the pinned producer's types before accepting a primary ID; malformed entries, duplicate identities within a finding or conflicting required-CVE sources refuse the control. Scores accept finite JSON numbers, excluding booleans, without imposing new ranges or interpreting date strings. Required CVSS vendor metadata and unknown extra fields retain their original values. Absent, null or empty related lists preserve primary-ID controls. Original primary IDs, related metadata, report bytes and hashes remain unchanged; this check neither rewrites advisories nor changes the severity gate.

The isolated Grype runtime strips inherited GRYPE/SYFT configuration and proxy variables, verifies and extracts only the bounded regular executable into a private exclusive directory, and checks its native version and identity. It requires a new successful official database update for every invocation, validates integrity and a build age of at most 24 hours, then disables automatic updates and checks the same database bytes before and after all queries. No stale fallback, ignore rule, exclusion, VEX or fixed-only filter is permitted. The frozen configuration requires `match-upstream-kernel-headers: true` to prevent the [pinned producer's default](https://github.com/anchore/grype/blob/6f8d854af29d3a3086b11a84afa51554a2a245fe/cmd/grype/cli/commands/root.go#L146) from appending four kernel-header ignore rules; upstream kernel-header matches remain visible and the effective ignore list must stay empty. The invocation budget is 600 seconds, at most 32 queries and 128 MiB per JSON report. Its shared process primitives observe a POSIX group leader without reaping before group termination, abandon uncertain ownership without later signaling or waiting, and give reader threads private duplicated FDs. Timeout, cancellation or cleanup refusal cannot announce accepted evidence. Raw reports survive refusals, but source, identity, configuration, database, coverage, drift or cleanup failures cannot leave accepted metadata.

The hash-checked official Grype 0.120.1 release archives contain four regular members: `CHANGELOG.md`, `LICENSE`, `README.md` and `grype`. The reader permits only these exact names, rejects duplicates and additional or extended headers, and bounds each metadata member to 1 MiB and the executable to the existing 256 MiB limit. Only `grype` is extracted; the metadata members never become files in the private runtime directory.

An interrupted or ambiguous reader start aborts the first invocation without retries or accepted evidence. A retained exception traceback can retain at most two private duplicated FDs until its final references disappear or the process exits; the parent never closes a transferred reader FD using a potentially reused number. Successful collection requires both readers to finish and close their own descriptors. ClickHouse also compares the created container's configured environment exactly to the selected image configuration before execution and after exit; only `env_matches_image: true` is recorded, with no environment values in receipts or diagnostics. This checks Docker configuration inheritance, not the complete environment constructed by the kernel or runtime during execution.

After a ClickHouse client reports uncertain process ownership or failed process cleanup, the observer latches that refusal and launches no additional Docker client, including during container cleanup. The invocation fails without a receipt; an already created helper can remain for disposal with the isolated hosted CI machine. Ordinary command failures with completed process disposal still attempt the guarded immutable-container cleanup.

It checks the recorded effective configuration, database age/file-table receipt, exact query reports, controls and all current source hashes, then disposes the OCI workspace before writing the manifest. Internal-main signing revalidates this manifest, signs both the original OCI archive and the separate evidence manifest, and verifies both with the same repository/workflow/source constraints. To verify the latter after download, run the earlier `gh attestation verify` command with `IMAGE.evidence-manifest.json` and its corresponding evidence bundle. This authenticates recorded scanner evidence and source identity; it does not rerun the advisory database or certify absence of all vulnerabilities. Real native tool queries, both architecture scans and signatures remain mandatory CI evidence; local fixture tests do not produce those results.

`scan-images.py --input ARCHIVE --image api|worker|collector|test|frontend|postgres|clickhouse|redis|node-exporter --platform linux/amd64|linux/arm64` uses Trivy's complete `--list-all-pkgs` JSON inventory. Local ShadAI wheels are covered by the image SBOM without querying an unrelated public package of the same name. The eight maintained-service builds preserve exact native OS and versioned Go dependency coverage and require the separately assigned generic, source-projected or declared principal queries; a missing principal SBOM entry is never presented as native package coverage. No replaced official service base is deployed or presented as a scanned runtime. Infrastructure scans separately include the externally pulled immutable Prometheus runtime. Its JSON inventory must exactly match a paired Trivy CycloneDX inventory for the same immutable reference/config digest/platform. It materializes only the canonical OCI files without changing an index, descriptor, statement or blob. The sidecar binds the helper and table hashes and is written only after owned cleanup succeeds. A scan, identity, drift or cleanup refusal fails the gate; handled cancellation retains the primary error. The final test image runs the hash-locked dependency and local-project installs, `pip check` and imports of pytest, ShadAI and the standalone agent before uninstalling pip completely and removing the complete standard-library ensurepip package, including its bundled bootstrap pip wheel. A second smoke check requires both installer modules, their package directories, pip metadata and command scripts, and bootstrap pip wheels to be absent from the merged runtime filesystem. A subject-bound Trivy scan now precedes validation of the independently generated package inventory. If that inventory has an unsupported or incomplete shape, the raw diagnostic report is retained, while the gate fails and publishes no accepted metadata sidecar. Source, subject, layout, package-coverage and lock validation is required before accepted metadata is written; that sidecar binds valid findings even when severe advisories fail the gate and does not certify a passing gate.

The private Grype workspace remains bounded to 4 GiB in total and 128 entries throughout database download and extraction. Only the exact basename `vulnerability.db` may use a per-file cap equal to that existing 4 GiB total, including temporary copies anywhere inside the anchored private tree and the final adopted SQLite file. Every other file, including import metadata, retains the 2 GiB per-file cap and its independent smaller JSON, configuration or asset limits. The same type, link-count, identity, final-directory-shape and cleanup checks apply. A SQLite file plus compressed downloads, binaries or other files that exceed the total still fails; this bound does not certify that a future official database or its update peak will fit, or finish within the unchanged 600-second invocation budget.

On failure, the scanner also attempts to create one exclusive private `image-scan.UUID.failure.json` file in the existing audit directory. This unsigned diagnostic is bounded to 2 KiB and contains only a closed stage, an exact allowlisted exception category, a fixed refusal code and an optional fixed cleanup-failure indicator. A trusted Grype preparation refusal can include a closed preparation phase and filesystem reason, distinguishing an unexpected private-directory entry from a regular-file, hardlink, namespace or system-call refusal. The workspace-tree refusal distinguishes a nonregular entry, zero links, multiple links and a regular file exceeding its applicable per-file limit, using the same stat observation that caused rejection; it does not infer which native entry or operation caused that observation. Missing or untrusted detail is omitted; a generic filesystem refusal does not prove which native command was reached. It captures the first refusal before disposal without exporting exception messages, commands, paths, environment values or package contents. Failure to write this diagnostic preserves the original error or cancellation. This file is never accepted scan evidence or a signing input; successful scans produce no failure diagnostic, and every existing coverage, advisory and cleanup gate still controls acceptance.

A converted Grype preparation system-call refusal may additionally include `filesystem_exception`, containing only a fixed exception family and errno category. Exact trusted operating-system exceptions map to `not_found`, `permission`, `resource_limit`, `busy`, `interrupted`, `io`, `invalid`, `other` or `unavailable`; exact trusted tar exceptions and unsupported exception types disclose no errno. The snapshot is taken before cleanup. The field is omitted outside an eligible preparation failure, for untrusted or malformed detail, or when it would exceed the existing 2 KiB bound, preserving the earlier diagnostic. It exports no raw errno, message, filename or Windows error code. This diagnostic does not identify a specific failing filesystem operation, establish its cause or fix it; the native errno behind the currently observed update refusal remains unknown until a new bound run reports it.

Fresh scans clear any previous report before invocation and retain a metadata sidecar binding the invocation, command, exact source commit/repository, scanner pin/version, scanner-script hash, input/lock/manifest hashes, report hash and expected inventory. CI passes `--source-commit` and `--repository` explicitly; local execution records the checkout's HEAD and whether source changes are present. A dirty checkout produces local development evidence, which cannot establish an immutable release proof for that HEAD. Previously retained reports without those sidecars can establish their observed advisory contents and shape, but require a fresh bound scan before publication evidence is accepted. Unfixed/less severe findings remain visible in artifacts and require an explicit operational decision; passing a gate is time-specific advisory evidence, not absence of all vulnerabilities. The existing embedded `braces` 3.0.3 residual in frontend build-tool bundles remains an explicit exception requiring the established literal-path/watch restrictions and separate review. A zero named-package npm audit does not prove those bundled bytes were removed, and these gates do not erase that residual.

Before accepting a dependency/image update, run normal Ruff/backend tests, clean frontend tests/build, native Windows guards, full Compose startup/smokes, offline agent checks, both architecture image builds and all new security/evidence gates at the exact reviewed commit. Local static/unit evidence cannot replace daemon-backed builds, real-store behavior or platform-native qualification.
