# Production qualification

Laboratory qualification is a disposable rehearsal. It measures neither a real installation's capacity or RPO/RTO nor the representativeness of Microsoft signals or the corpus. Check the mandatory `production-qualification` job for the deployed commit. The local Docker engine was stopped during development; no local execution of stores, OOM or restoration is claimed.

<a id="démarrage-et-mise-à-niveau"></a>
## Startup and upgrade

On a fresh installation, start stores, catalog migration and new workers without waiting for global readiness. Their initialization creates the actual Redis groups. Then reconcile in the configured environment before declaring the installation ready or enabling collectors:

```bash
docker compose up -d --build
docker compose exec -T api python /app/entrypoint.py python -m shadai.workers.redis_lifecycle reconcile --execute --legacy-writers-stopped
docker compose up -d --wait --wait-timeout 180 api ingest-worker correlation-worker purge-worker frontend
```

If groups are not initialized yet, wait for their creation and retry reconciliation; do not fabricate readiness. For an upgrade, stop **all** legacy writers, workers and replay clients before starting the new version and this command. Without a valid schema, ACK conservatively retains sources; retention can reach the admission cap. Writers must stop before stores in a cold backup. See [the Redis contract](queue-retention.md).

<a id="laboratoire-isolé"></a>
## Isolated laboratory

A nonroot Linux host, Docker and Compose v2 are required. The laboratory API, workers and inspectors use the host UID/GID to read private secrets; the report distinguishes this UID from the delivered runtime, `10001`. Stores use their official entrypoints. No Docker socket is mounted in containers.

```bash
python scripts/qualification-lab.py plan --profile deploy/qualification/profiles/lab-smoke.json --run-dir "$HOME/qualification-new"
python scripts/qualification-lab.py run --execute --docker-context default --profile deploy/qualification/profiles/lab-smoke.json --run-dir "$HOME/qualification-new"
python scripts/qualification-lab.py resume --execute --docker-context default --profile deploy/qualification/profiles/lab-smoke.json --run-dir "$HOME/qualification-new"
python scripts/qualification-lab.py clean --docker-context default --profile deploy/qualification/profiles/lab-smoke.json --run-dir "$HOME/qualification-new"
python scripts/qualification-lab.py clean --execute --remove-volumes --docker-context default --profile deploy/qualification/profiles/lab-smoke.json --run-dir "$HOME/qualification-new"
```

The directory must be new; it is created as `0700`, with files `0600`. A UUID identifies source and restore projects and their labels. The journal verifies IDs, creation time, labels, context, profile, code and secrets on resume. Cancellation retains volumes and phase state. Cleanup revalidates every resource; volumes require `--remove-volumes` as well as `--execute`. No global `compose down`, volume wildcard or directory deletion is used.

Inspectors remain one-off containers while writers are stopped. Their generated name supports inspection verifying project, UUID, role, service, creation time, full ID and image identity before any wait/logs/cleanup. `compose run` output may contain build progress; it never serves as identity. Name collisions or invalid identities are refused, and cleanup uses only the verified immutable ID.

Before its first `XAUTOCLAIM` on each stream, a worker explicitly registers its consumer with `XGROUP CREATECONSUMER`. Only exact integer results `0` or `1` permit continuation; failure or cancellation leaves that stream unregistered for the next attempt. The laboratory initializer creates only groups and never polls. Result `0` does not prove that a legacy consumer created by an empty claim had already persisted.

After the pending fixture and before source inventory, the owned `redis_persistence` inspector waits for an idle period, then runs `BGREWRITEAOF` once. Writers remain stopped through inventory and store shutdown/export. Each sample uses atomic `INFO server persistence`, fully validated before comparison. Proof requires the same Redis process, enabled AOF, no write error, exactly one additional rewrite generation completed successfully, no active or scheduled save/rewrite, and empty pending buffer/fsync. The 120-second and 480-total-sample limit, with 250 ms pauses, covers initial wait and follow-up; the laboratory retains its deadline and checks its budget before launch and after result. Redis identity and INFO fields stay private; only `redis_persistence_complete=true` is accepted. Complete inventory assertion and all six group fields are retained.

Unknown INFO metadata may contain builtin dictionaries and lists from the Redis decoder, including listeners. Its complete graph is validated before reading or comparing evidence fields: depth 8 from root 0, 4,096 node occurrences, 256 entries per dictionary/list, 128-character keys, 4,096-character strings and 65,536 combined text characters. Integers remain bounded to 63 bits and floats must be finite; booleans, nulls, other types, subclasses and cycles are refused. Every occurrence of a shared alias consumes the budget again. No unknown field is removed or modified; required fields retain exact types and values.

Mandatory Linux Python jobs run three native regressions on the pinned Redis digest, with AOF enabled and RDB snapshots disabled: expected reproduction of consumer loss after empty claim, persistence after explicit registration, then legacy-consumer persistence after completed checkpoint. Volumes/containers are disposable, nonce-owned, without network or published ports; unconfirmed cleanup fails. Complete groups are compared privately. Missing Docker on Linux fails; Windows may only mark these three proofs skipped. These tests do not replace the full cold restore in `production-qualification`; its exact assertion must also pass.

An ordinary native-proof, startup or cleanup failure leaves the private context before raising a fixed refusal, without retaining the original exception or its INFO/group/client frames. Short, long, local-variable or complete tracebacks must disclose no private data. Cancellations retain their original exception and owned cleanup remains mandatory. Graph compatibility and these privacy controls are source checks; native proof of all three cases on both CI Python versions and exact cold restore remain required after changes.

The CI profile emits **1,000 synthetic events, 10/s, batches of 10, concurrency 2**, with a 5-second total request timeout and 120-second drain. Budgets are 1,500 s, 500 requests, 2 MiB per request and 10 GiB of files. These are test inputs, not advertised capacity. UUID5 IDs and retained bytes identify each retry; the report distinguishes attempts, HTTP acceptances, unique logical persistence, physical rows, receipts, HTTP latency and latency to PostgreSQL receipt.

The monotonic deadline starts before fixture preparation. Every POST and target/readiness GET uses an isolated stdlib subprocess, without environment proxies or redirects, with verified TLS and a 64 KiB response cap. URL, key and bytes pass only through bounded stdin; no provider data is logged. Slow DNS, headers and body share the minimum of request timeout and remaining budget. On timeout or cancellation, the child is killed and reaped within a separate cleanup budget of at most 1 s per child, with bounded concurrency. An expired request is never counted as accepted; its server result remains unconfirmed.

Mandatory scenarios run load, ingestion stop/resume, correlation stop, consumer stop after PEL proof, then reclaim. Restore stops all writers/stores, archives owned volumes read-only, validates every path/link/hash before import into new volumes, compares inventories before workers, then verifies new writes and pending work. Internal relative ClickHouse links are preserved; absolute paths, traversal, outgoing links, devices and FIFOs are refused. Archive helpers have no network, a read-only rootfs and targeted `DAC_READ_SEARCH`, then `CHOWN/FOWNER` capabilities for import. Export writes to a separate new run-owned output volume mounted writable at `/export`; the source volume remains read-only. That volume retains the archive after helper shutdown, unlike `/tmp` tmpfs. Before writing, `RLIMIT_FSIZE` bounds each file to remaining run capacity, capped at 1 GiB; the content budget preserves its 10 MiB header reserve. Copy uses the verified stopped-helper ID and checks size/SHA-256 before deleting the output volume. Import retains the existing read-only host-archive mount at `/archive.tar`.

Restore requires ten new distinct acceptances, their ClickHouse rows, ingestion/correlation receipts and the backed-up PEL event. Pending recovery alone is insufficient. Disk budget covers the sum of regular private run files, checked before copy/import and after copy; links are refused. Each export receives the remaining budget minus 10 MiB metadata reserve, with at most 1 GiB in the helper tmpfs. Volume data and other tmpfs measurements/limits are separate; this artifact cap is not a global physical store limit.

Cold diagnostics add `cold_restore_*` checkpoints from fixed lists: entry budget, shutdowns, pending fixture, inventories, export/import, manifest/secrets, startups, readiness and verification of eleven references. Possible Docker operations and services are also closed; the last completed Docker checkpoint may be shown. The first failure is frozen before `finally` blocks, with at most one closed secondary failure and a total envelope of at most 2 KiB. No helper output, data, identity, URL, path or exception message is added. Diagnostic failure retains original exception/cancellation; existing cleanup propagation rules remain unchanged. These fields provide no restore proof, change no call/guard/deadline/budget and never replace the eleven required persistence/receipt/correlation results.

An exact assertion failure before workers start may add `inventory_comparison`: equality booleans by store/component, with PostgreSQL/ClickHouse row counts and Redis counts of keys, hash fields, zset members, stream entries, groups and pending. A missing PostgreSQL table has count `-1`, distinct from an empty table. Private keys/values never appear; ordering and associations remain part of comparison. Both inventories must first satisfy producer shapes and cycle-free builtin JSON validation, bounded jointly to 100,000 values/keys, depth 32, 1 MiB characters and 4,096-bit integers. Refused shape/budget omits the optional field; assertion, message, exception and failed status remain unchanged. The summary locates a difference without establishing its cause, fixing it or qualifying native restore.

If Redis groups differ, that summary may add `redis_group_fields`: `aligned`, six equality booleans for `name`, `consumers`, `pending`, `last-delivered-id`, `entries-read`, `lag`, and two booleans indicating unknown fields on either side. Alignment requires identical stream keys and group counts per key; groups compare at original positions, without sorting or name matching. Without alignment all six flags are false and cannot attribute the difference to a field. Unknown fields/values remain in complete comparison but are never published. All six known fields must be present and exactly typed; `entries-read` and `lag` may be null. Refused shape or a complete envelope exceeding 2 KiB, including secondary failure, omits only this detail and preserves the existing summary. Schema remains version 1; an old validator rejecting additional keys may reject enriched diagnostics. This detail fixes no difference and is not native proof of successful restore.

If export helper fails, `cold_restore_export_result` may add `helper_exit_status` (integer 1–255), `helper_step`, `helper_reason`. The qualification wrapper enables a private context and replaces only the closed CLI error JSON line with an ASCII diagnostic of at most 768 bytes. Injected `print` belongs solely to the `runpy` namespace; healthy prints retain their arguments/bytes. Ordinary CLI is unchanged. The laboratory parses the complete captured output, with fixed keys/types/values and no duplicates; missing, mixed, invalid or oversized output becomes `diagnostic_unavailable`. Steps distinguish source guard, opening, inventory, headers, validation, writing, closes, reread, hash and result. Refusal reasons correspond to existing guards; `operation_error` locates an operation without attributing its system cause. First failure precedes closes; only one secondary failure is retained, including helper failure. No message, path, argument or content is published. These details change neither failed status nor guards/calls/deadlines/budgets/eleven-reference requirements; they do not prove successful native restore.

Metadata refusal distinguishes the first true guard branch: `metadata_duplicate_name`, `metadata_mode`, `metadata_uid`, `metadata_gid`, `metadata_size`. Diagnostics record only already evaluated boolean decisions without rereading attributes; no mode, UID, GID or size is published. Guard order, other metadata predicates and refusal message stay identical. Historical `metadata_guard` remains accepted. A mode reason does not identify which bits were present.

Archive mode must be an exact Python integer. Ordinary permissions are accepted; SGID and sticky are preserved only for an exact `tarfile.TarInfo` whose type is exactly the directory marker in `bytes`. SUID is always refused, as is any special bit on a file/link/other object. No bit is stripped or normalized. Import validates metadata before any write; extraction first keeps private ownership and `0700`/`0600` modes, then restores ownership before mode, deepest first and root last. This requires an exclusively owned quiescent restore volume; it does not guarantee safety against a hostile same-UID process or concurrent filesystem mutations. No directory descriptor is retained to provide that guarantee.

The three chained comparisons remain evaluated in conditional context before recording a boolean. Source checks include a false lower bound, a truth result changing on its second call and cancellation on that second call; they are not native proof of the subtype encountered.

Pressure Redis is **separate**, 32 MiB, `noeviction`, AOF, without published ports. `redis_pressure` tests run seed/assert phases, including SSO refusal under OOM. `SHADAI_REQUIRE_REDIS_PRESSURE=1` makes prerequisites mandatory; missing/skipped tests prevent success. The IDs/hashes manifest is private/shared and read-only during assert. The AOF clone must restart another Redis process. Normal Redis is never reconfigured for pressure.

OOM refusal is a **controlled injection in this laboratory**, not certification of saturation at 32 MiB. After verifying target/configuration, the helper fills only owned keys without TTL, within 256 writes and 64 MiB. It measures effective heap (`used_memory - mem_not_counted_for_evict`), then temporarily lowers `maxmemory` to heap minus 1 MiB, without exceeding the initial limit. INFO must confirm heap above that limit before real assertions of Redis refusal, SSO 503 and retained state. Measured values and confirmed restoration appear in JUnit/seed manifest. Independent budgets are 10 s prerequisites, 30 s injection, 60 s assertions. Every exit, including error/cancellation, reserves up to 5 s for each of three operations: restore exactly 32 MiB, remove/verify only owned fillers, then verify `noeviction`, AOF and restored limit. Refused restoration/cleanup fails; a primary error retains identity and receives only fixed notes.

Docker failure in this flow adds a fixed-list checkpoint/operation and last completed Docker checkpoint to existing `report.json` diagnostics. They distinguish seed/assert helpers, store shutdown and AOF export/import without publishing arguments, environment, paths, Docker output or private journal. They locate a failed call and do not prove restoration. Secondary discovery/cleanup failure retains primary cause; secondary interruption remains interruption. Identity checks, budgets and pressure assertions remain mandatory.

`pressure-test` and `pressure-assert` helpers refuse collisions before creation, then resolve generated names after `compose run --build` without using its output. Project/UUID, pressure role, exact service, creation time, name, full ID and image are verified before journaling/waiting. Wait, revalidation and removal use only verified immutable ID. Exact name/image expectations persist in the journal and are revalidated during later resume/cleanup for inspectors and both pressure helpers. An old helper record missing those proofs is refused; expectations are never invented from current state. Interruption cleans up the owned helper; changed identity remains journaled and blocks cleanup. Refused cleanup never becomes success and preserves primary cause with a fixed note, without Docker output/secrets. These unit tests do not prove actual pressure/restore execution, which remains mandatory in CI.

`report.json` contains required/executed/status scenarios, profile/code hashes, environment, measurements and missing evidence. Codes: **0** criteria met; **1** failed measurement/criterion; **2** missing prerequisite/evidence. Explicit optional objectives (`max_http_p95_seconds`, `max_end_to_end_p95_seconds`, `max_recovery_seconds`, `max_restore_seconds`, `minimum_precision`, `minimum_recall`) never pass without measurement. Keep archives, fixtures, inventories and secrets private; published CI artifacts contain only report, source hashes and JUnit.

A failure after preparation and before first scenario appears in `evidence.failure`: phase, fixed step, allowlisted error type, fixed code and bounded exit code where available. Diagnostics distinguish Compose, resource discovery, initialization, readiness and enrollment. If both Compose and discovery fail, Compose remains primary and discovery appears in `secondary`. No argument, URL, secret, exception message, stdout or stderr enters this diagnostic; Docker errors use `docker_nonzero`, `docker_timeout`, `docker_process_error`, `docker_output_budget`. Diagnostics replace no missing evidence and never make the run successful.

<a id="sondes-par-processus"></a>
## Per-process probes

Each worker publishes at most 4 KiB under `/tmp/shadai-probe`, directory `0700`, file `0600`, by atomic replacement. No event, account, DSN or provider error appears. PID, startup ticks and boot ID prevent identity reuse. Heartbeat originates in the same asyncio loop every 5 s.

Startup requires actual initialization; liveness requires a 0–30 s heartbeat and contacts no store. Readiness requires local progress: poll ≤90 s or handler ≤300 s, and known dependencies/states for each stream, including `retention_ready`. Store failure leaves the process alive and unready. Purge requires a **successful** cycle within 27 h and a bounded phase; exception followed by sleep is not success. `SHADAI_PROBE_*` budgets are validated. Exec readiness passes through `/app/entrypoint.py` to resolve secrets; it does not inherit DSNs modified in the worker process.

A `probes` scenario failure adds constants in `evidence.failure`: checkpoint, operation, allowlisted service when known and last completed checkpoint. They distinguish dependency registry/identity, migration state, store health, budget, worker probes, peer launch/discovery, suspension/resume and witness helper. First diagnostic freezes before `finally`; a secondary failure appears in one `secondary` envelope without changing exception/cancellation propagation. Diagnostics are capped at 2 KiB and include no ID, argument, environment, path, output, note or exception message. They prove no probe success and replace no identity/deadline/missing-evidence check.

The readiness command retains its exit code and emits a small fixed-reason envelope only on failure. The laboratory validates that envelope (256 bytes maximum, exact keys, no duplicates) on readiness refusal after dependency restart. `reason_code` distinguishes invalid record, initialization, heartbeat, phase/progress and dependency checks; `secondary_reason` identifies possible cleanup refusal. Missing, log-mixed, invalid or oversized output becomes `diagnostic_unavailable`; forced alarm and entrypoint refusal before the module may also have no reason. These constants never make a probe healthy and are not identity or restore proof.

After Redis resumes, healthy stores do not guarantee the worker has published its recovered phase. The laboratory waits only for actual readiness refusal with `phase_unready` and `secondary_reason=none`, within the existing 120-second monotonic window shared with dependencies/peer launch and capped by remaining budget. Every round revalidates migration identity/state, store identity/health, then worker identity; no new launch/restart is added. Prior-attempt diagnostics are cleared before the next. The peer starts only after actual zero readiness exit and a fresh budget check. Any other reason, invalid output, inspect/exec error or cancellation still blocks; sustained unready phase exhausts the same deadline without a peer. Heartbeat guards and worker-health criteria stay unchanged.

An empty stream read uses `XREADGROUP BLOCK 1000`, leaving margin under the Redis client's 5-second timeout. Only completed reads update poll; errors or ongoing waits retain the last actual progress. Heartbeat may remain healthy during store outage without making absent poll/cycle timestamps ready.

The laboratory verifies SIGSTOP with a second healthy replica, an asynchronously suspended handler alive/unready and a Redis outage without increased restart count.

After Redis restarts, the second replica launches with `compose up --no-deps`, recreating no registered dependency. Before launch, the laboratory revalidates unique identities of `migrate`, Redis and ClickHouse; migration must have completed with exact integer zero exit, and both stores must be running/healthy. Only health `starting` permits another read after at most one second. Original-worker actual readiness must then pass under the same identity. Checks and launch share at most 120 seconds, capped by remaining global budget. Missing/foreign/duplicate identity or invalid state blocks launch; the journal adopts no replacement and deletes no old ID. This source check is not proof of native Docker laboratory success.

Subcommands/waits use remaining global budget. Resuming the deliberately suspended process and stopping its peer have a separate safety-cleanup budget of 10 s: revalidating IDs, actually issuing Docker SIGCONT and stopping the peer requires several daemon round trips. Cleanup does not make an interrupted scenario successful. CI work budget is 1,500 s; added termination budgets are at most 12 s (10 s Docker and conservatively two 1-second HTTP cleanups), a declared application ceiling of **1,512 s**. No target-qualification browser is launched.

<a id="mesures-physiques"></a>
## Physical measurements

[The optional host profile](../docker-compose.host-monitoring.yml) is Linux-only, without public ports, with read-only host mounts. It builds the maintained recipe from official [node_exporter 1.12.1](https://github.com/prometheus/node_exporter/releases/tag/v1.12.1) sources, Go 1.26.6, x/crypto 0.55.0 and x/text 0.41.0, memory/filesystem collectors only. The local tag identifies that recipe; its official base index and exact inputs are recorded in `requirements/images.json` and the [maintenance manifest](../requirements/service-builds/manifest.json). Final images for both architectures must pass OCI/SBOM evidence and CI scans. The [official Dockerfile](https://github.com/prometheus/node_exporter/blob/v1.12.1/Dockerfile) specifies entrypoint/user. Prometheus uses a separate job/rules.

```bash
docker compose -f docker-compose.host-monitoring.yml up -d
```

The laboratory compares actual scrape to `/proc/meminfo` and `statvfs(/)`: equal totals, temporal tolerance 5% available memory and 1% available disk, floor 64 MiB. It also measures Docker stats, Redis `INFO memory` and each owned volume's `statvfs`. Redis RSS, Docker usage/cache, limits and filesystem space stay distinct; multiple volumes on one filesystem are not added together. Kubernetes may use existing `kubelet_volume_stats_available_bytes/capacity_bytes`; if absent, space is **unknown**, with no invented physical application gauge.

If this scenario fails, `evidence.failure` contains a fixed physical checkpoint, Docker operation and last completed checkpoint. Constants distinguish inspector, seven measured services, volume helpers and exporter; no ID, argument, environment, output or exception message is published. Secondary cleanup/discovery errors stay separate from primary; interruption remains interruption. Diagnostics validate no missing physical measurement.

<a id="qualité-du-catalogue"></a>
## Catalog quality

```bash
python -m shadai.qualification quality --corpus deploy/qualification/corpora/synthetic-reference.jsonl --catalog catalog/builtin --output /chemin/prive/quality.json
```

The CLI actually calls `CatalogMatcher.resolve_event` and freezes catalog hashes. JSONL begins with a manifest of provenance, period, labelling method and sampling frame; each case contains source/protocol, canonical event, truth `true/false/null` and expected attribution. Duplicates, unknown fields, versions, nonfinite values and exceeded limits are refused. Bounds: corpus 64 MiB, case 64 KiB, 100,000 cases, catalog 16 MiB total/1 MiB per file.

Profile, YAML and corpus are read once, at most limit+1 byte, after checking regular nonlink files; POSIX also uses `NOFOLLOW/NONBLOCK` for concurrent replacements. Hashes correspond to the actual parsed/indexed bytes. No overrides subdirectory enters this frozen evaluation.

The delivered corpus is **SYNTHETIC**, without representativeness: TP=1, FP=1, FN=2, TN=1, precision=0.5, recall=1/3, F1=0.4. An abstained or signal-free positive is FN. Unknown truth is excluded from supervised denominators but included in coverage. Zero denominator → `null` with reason. Ambiguity, no signal and attribution errors stay separate. Per-case report contains only ID/status/attribution. These metrics describe normalized metadata matching, not capture, actual model use or calibrated probability.

<a id="installation-réelle"></a>
## Real installation

```bash
python -m shadai.qualification target plan --plan deploy/qualification/profiles/target-plan.json --output /chemin/prive/plan.json
python -m shadai.qualification target preflight --plan /chemin/prive/target.json --output /chemin/prive/preflight.json
python -m shadai.qualification target load --execute --plan /chemin/prive/target.json --output /chemin/prive/load.json
python -m shadai.qualification target kubernetes --execute --plan /chemin/prive/target.json --output /chemin/prive/kube.json
python -m shadai.qualification target idp --plan /chemin/prive/target.json --output /chemin/prive/idp-metadata.json
python -m shadai.qualification target evaluate --plan /chemin/prive/target.json --evidence /chemin/prive/evidence.json --output /chemin/prive/evaluation.json
```

Without `--execute`, load sends nothing and Kubernetes renders without apply. With `--execute`, Kubernetes performs a **server dry-run** and nodes/pods/endpoints/NetworkPolicy inventory on the exact context/namespace. It does not modify the cluster. Rendered profile has API/frontend/ingestion/correlation ×2, purge ×1, PDB minAvailable=1, mandatory hostname anti-affinity, maxSurge=0/maxUnavailable=1, dedicated external stores, legacy disabled, Secure cookies and digest images. This does not prove HA: scheduling, ingress/TLS, network, probes and node/store failures remain target evidence under a maintenance plan and explicit objectives.

`target` requires `namespace`, `kubernetes_context`, `origin`, `issuer`, `stores` (postgres/redis/clickhouse IDs), `images` (api/frontend/worker), explicit `egress_cidrs`, `runtime_secret_name`, `tls_secret_name`, exact `ingress_namespace` and `ingress_pod_selector`. Both ingress selectors intersect. Placeholders and `/0` egress are refused. Existing runtime Secret supplies database_url, redis_url, clickhouse_host/user/database, jwt_secret, encryption_key, ch_password, oidc_client_id/secret; no secret mounts into frontend. Do not broaden `TRUSTED_PROXY_IPS` to pass the test; make exact ingress overwrite headers. Store TLS and SCIM policies still require target configuration/verification.

`secret_files` contains only absolute private local paths: `collector_key` (JSON collector_id/api_key/run_id for a dedicated **existing** collector), `run_directory_marker` (private file in a `0700` directory). Target action has one monotonic deadline starting before preparation; GET/kubectl use remaining budget. `idp` without `--execute` verifies only health/readiness and exact-issuer OIDC metadata with bounded GETs. It qualifies neither login, session nor MFA.

`idp --execute` is disabled on all platforms: refusal `unsupported_browser_containment`, result `not_evaluated`, exit 2, before GET, Node/Chromium launch or account-reference reads. Chromium starts in another POSIX session/group; stopping Node's group does not prove Chromium stopped. The retained JavaScript helper returns only that refusal without reading arguments or writing evidence. A non-detached-descendant cleanup test does not qualify Chromium. Actual human login/MFA, fresh return, session/me, HttpOnly/Secure cookies, CSRF/logout and role/deactivation propagation require authorized observations on the real target. `target evaluate` never converts caller-supplied JSON success flags into independent proof.
